# Product

## Problem

Teams use three or four different tools for observability (APM, RUM, logs, load testing) and define alerts by hand, usually
after an incident has happened. When a new endpoint is added, no alert is added; load tests run in a separate world and
their results cannot be compared with production telemetry.

## Solution

One SDK family + one platform:
- Add the SDK → backend/worker/consumer/web/mobile data flows automatically.
- Connect the repo → the platform extracts the endpoint and consumer inventory, identifies critical paths, and suggests alerts.
- Generate a load test scenario from the same inventory, run it, and see the result side by side with live telemetry.
- **Define KPIs** ("the home page should load fast", "checkout should succeed") → alerts are built on the KPI's error budget.
- **Root cause analysis:** when a KPI degrades or a service's error rate / latency rises, the platform walks down the call tree
  to the lowest layer and names the problem: *"the home page is slow because storefront-bff → recommendation-api →
  reco-db queries got 63× slower (migration 0042 dropped the index)"*. On the service page it directly answers "is it your
  code, or a service you call?". Details: [`alerting.md` § KPIs](alerting.md#kpis-slo) and
  [§ Root cause analysis](alerting.md#root-cause-analysis).

### One place rule

The same item (list, "New …" button) exists in exactly one place in the interface. KPIs, alerts and logs live in the tabs of
the service that owns them; "New KPI" only in the KPIs tab, "New monitor" only in the Alerts tab. Infra alerts (kind `infra`) live under
the item they watch: the Alerts section of a host or database page and the Alerts tab of a Kubernetes cluster. A rule without
that item's filter (e.g. "every host") applies to all of them and is listed on each. Overview shows a cross-service
summary (open incidents, golden signals, service table); the aggregated view of KPIs is only at `/kpis`.

### Frontend = service

Web and mobile apps are not in a separate "Frontend" section; they are in the **service list** (type: `web` / `mobile`).
An organization can have any number of client apps (storefront, backoffice, seller portal, courier app, landing...).
A client app's service page is the RUM view: KPIs, users, vitals, pages/screens, sessions, errors and
**API calls** (the backend endpoints the app calls — the transition from frontend to backend happens here).

## Personas

| Persona | Need |
|---|---|
| **Backend developer** | Is my endpoint slow, is it failing, after which deploy did it break? |
| **Frontend/mobile developer** | Which page opens slowly, which screen has a crash, where does the user flow drop off? |
| **SRE / platform** | Low alert noise, high coverage; capacity limits are known. |
| **Product / manager** | How many users, which pages, session durations, overall health. |

## Collected data

### Backend (HTTP service)
- Request count, status code distribution, latency histogram — per route template
- Trace/span (DB, cache, external HTTP, queue publish)
- Exception (stack trace, fingerprint)
- Runtime: CPU, memory, GC, goroutine/event-loop lag, pool usage
- Deploy marker (version, commit sha)

### Worker / Consumer
- Message processing rate, processing time, success/error, retry, sent to DLQ
- Consumer lag (topic/partition), queue depth
- Cron/job: last successful run, duration, missed run
- **Model: no endpoints, processes.** A worker/consumer does not receive HTTP requests; it listens to a data source (Kafka topic, RabbitMQ/SQS queue, cron schedule). The unit = **process** (each with its own consumer group); the topic it reads is a separate field. Multiple processes can read the same topic (e.g. `orders.created` → `order-created-handler`, `order-search-indexer`).
- Service page: **Processes** tab (Process + group/schedule · Reads from (source + topic, "+N more reader") · msg/min · lag · error · p95 · retry/DLQ). In Traffic flow the incoming side "Reads from" = topics (the producing service as `via`), not services.
- Lag, alerts and monitors are bound to the **process** (`svc · process`), not the topic — lag is per consumer group.
- **Lag** tab on the consumer page: for each (topic, consumer group) the service reads, a lag time series, lag per partition, produce/consume rate, catch-up ("not catching up" / "drains in X" / "≈ X s behind") and suggestions (hot partition, members < partitions, rebalance, consumer without SDK). Lag is read from the broker (Infrastructure → Message queues).

### Web (browser SDK)
- Page view, route change (SPA), referrer, UTM
- Web Vitals: LCP, INP, CLS, FCP, TTFB
- Resource/XHR/fetch timings → linked to the backend trace (traceparent)
- JS errors (resolved with source maps), unhandled rejection
- User: anonymous id, user id/email via `identify()` (opt-in), device, browser, country
- Session: duration, page count, bounce, rage/dead click
- Custom event (`track('checkout_started')`)

### Mobile (React Native, then native iOS/Android)
- Screen view, app start (cold/warm), frame drop, ANR, crash
- Network calls, offline queue
- App version, OS, device model

### Logs
- SDK log bridge (pino, winston, zap, slog, console) or OTLP logs
- Automatic `trace_id` / `span_id` correlation
